= Compared to SV2 & DATUM
:page-nav_order: 4

A centralized pool running SV2 with Job Declaration or Ocean pool's
DATUM both enable pool operators to offload transaction selection to
miners. This decentralizes block template construction to miners
participating in the pool.

The following diagram captures the messages exchanged when a pool
supports DATUM Gateway or SV2 with Job Declaration. We do not get into
the exact message types specified by the two protocols, but capture
the abstract idea of decentralizing template construction.

[plantuml, datum-sv2-jobs, svg]
.Miners build templates, the pool accepts jobs and credits shares
....
@startuml
participant "Miner A\n(own bitcoind)" as A
participant "Pool operator\n(DATUM / SV2 JD server)" as P
participant "Miner B\n(own bitcoind)" as B

alt DATUM
  P -> A : coinbase outputs\n(payout split incl. miners)
  P -> B : coinbase outputs\n(payout split incl. miners)
  A -> A : build template\nfrom own mempool
  B -> B : build template\nfrom own mempool
else SV2 Job Declaration
  P -> A : pool's coinbase output\n(reward to pool wallet)
  P -> B : pool's coinbase output\n(reward to pool wallet)
  A -> A : build template\nfrom own mempool
  B -> B : build template\nfrom own mempool
  A -> P : declare job
  P --> A : job accepted
  B -> P : declare job
  P --> B : job accepted
end
loop while hashing
  A -> P : submit share
  P -> P : validate share,\ncredit Miner A
  B -> P : submit share
  P -> P : validate share,\ncredit Miner B
end
@enduml
....

== Centralised Pools Provide Permissioned Mining

Before we get into the details of how P2Poolv2 compares to SV2/DATUM
it is important to note that when miners join a centralised pool, by
definition they need a permission to join the pool and receive work or
payouts from them. A lot of pool operators are companies that need to
follow the regulatory environment they operate under. P2Poolv2 strives
to remain permissionless, where anyone can join the p2p network and
start mining with fully auditable accounting and payout mechanisms.

== Pools Control Payout Distribution

However, Ocean still manages the payout distribution when the DATUM
server notifies the DATUM gateways to include a provided bitcoin
coinbase output distribution.

A centralized pool operating with SV2's Job Declaration has the same
shortcoming.

In both cases the accounting and payout distribution end up being
controlled by a centralized pool operator. SV2 can be used in a more
decentralized model, but we haven't seen a pool design to support
that yet.

This is where the rubber meets the road. If a pool still decides on
block reward distribution, then it has a lever that can guide the
transaction selection behaviour of miners. When a centralized pool
operator comes under pressure from a regulator, it can be compelled to
comply and thus refuse to pay a miner that includes transactions
involving certain addresses or Script constructions that the
regulators want it to suppress.

The diagram below shows how under pressure from a regulator the
centralized pool operator refuses to pay a miner for their work and
leaves the miner the choice of dropping the transaction or leaving the
pool.

[plantuml, datum-sv2-payout-refused, svg]
.The pool leaves a miner out of the payout

@startuml
actor Regulator as R
participant "Pool operator\n(DATUM / SV2 JD server)" as P
participant "Miner A\n(own bitcoind)" as A
participant "Miner B\n(own bitcoind)" as B

A -> A : build template with\ntransaction paying X
B -> B : build template\nwithout X

  P -[#E5484D]> A : next coinbase outputs\n(Miner A left out)

  P -[#E5484D]> P : withhold Miner A's\naccount balance

end

@enduml

== Pools Can Reject Jobs

DATUM server validates the shares it accepts, so it has a final say in
what block templates it accepts as valid work.

In SV2's Job Declaration in Full-Template Mode, the pool operator can
outright reject jobs just like Ocean can with the DATUM protocol.

However, SV2's Job Declaration's Coinbase Only Mode allows a miner to
mine without sending the list of transactions to the pool operator. In
such setups the SV2 pool can't reject the work outright. This is the
most censorship resilient mode available to pools using SV2 and
P2Poolv2 sets this as the base guarantee to permissionless mining.

[plantuml, datum-sv2-work-rejected, svg]
.Whether the pool can reject work depends on what it can see
....
@startuml
actor Regulator as R
participant "Pool operator\n(DATUM / SV2 JD server)" as P
participant "Miner A\n(own bitcoind)" as A

R -[#E5484D]> P : suppress transactions\ninvolving address X
A -> A : build template with\ntransaction paying X
alt DATUM / SV2 full-template
  A -> P : declare job / submit share\n(transactions visible)
  P -[#E5484D]> P : check template\nagainst blocklist
  P -[#E5484D]-> A : rejected: template includes\nsuppressed transaction
  note over A : Miner A's work earns nothing\nunless it drops the transaction
else SV2 coinbase-only
  A -> P : declare coinbase / submit share\n(no transaction list)
  P --> A : accepted: pool can't\nsee transaction X
  note over P : Pool has to respond to the regulator
end
@enduml
....

== P2Poolv2 Decentralized Accounting

P2Poolv2 instead runs accounting using a decentralized share chain,
which is a blockchain of weak bitcoin blocks. With Nakamoto consensus
on the chain, all miners converge on the same view of shares and
therefore can generate payout distributions in coinbases that all
other miners can continuously and independently validate.

== P2Poolv2 Non-Custodial Payouts

With payouts directly from coinbases and also from an atomic swaps
mechanism miners never hand over custody of their shares or their
payout rewards to a pool operator, see
xref:payouts/marketplace.adoc[Marketplace] on how this is enabled in
P2Poolv2.

The only way P2Poolv2 can reject transactions is if it is 51% attacked
by miners who want to reject certain transactions. In that case, the
censored miners have the recourse to fork the pool and run a different
p2poolv2 chain.
