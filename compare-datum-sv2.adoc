= Compared to SV2 & DATUM
:page-nav_order: 4

SV2 with Job Declaration and OCEAN's DATUM both let a centralized pool
operator offload transaction selection to miners. Both decentralize
block template construction to the miners in the pool.

The following diagram shows the messages exchanged when a pool
supports DATUM Gateway or SV2 with Job Declaration. It leaves out the
exact message types each protocol specifies and captures only the idea
of decentralized template construction.

[plantuml, datum-sv2-jobs, svg]
.Miners build templates, the pool accepts jobs and credits shares
....
@startuml
participant "Miner A\n(own bitcoind)" as A
participant "Pool operator\n(DATUM / SV2 JD server)" as P
participant "Miner B\n(own bitcoind)" as B

alt DATUM
  P -> A : coinbase outputs\n(payout split incl. miners)
  P -> B : coinbase outputs\n(payout split incl. miners)
  A -> A : build template\nfrom own mempool
  B -> B : build template\nfrom own mempool
else SV2 Job Declaration
  P -> A : pool's coinbase output\n(reward to pool wallet)
  P -> B : pool's coinbase output\n(reward to pool wallet)
  A -> A : build template\nfrom own mempool
  B -> B : build template\nfrom own mempool
  A -> P : declare job
  P --> A : job accepted
  B -> P : declare job
  P --> B : job accepted
end
loop while hashing
  A -> P : submit share
  P -> P : validate share,\ncredit Miner A
  B -> P : submit share
  P -> P : validate share,\ncredit Miner B
end
@enduml
....

== Centralized Pools Provide Permissioned Mining

Miners who join a centralized pool need, by definition, the operator's
permission to join and to receive work or payouts. Many pool operators
are companies that must follow the regulations where they operate.
P2Poolv2 strives to remain permissionless: anyone can join the
peer-to-peer network and start mining, with fully auditable accounting
and payouts.

== Pools Control Payout Distribution

OCEAN, however, still manages the payout distribution: the DATUM
server tells the DATUM Gateways which coinbase outputs to include.

A centralized pool operating with SV2's Job Declaration has the same
shortcoming.

In both cases a centralized pool operator controls the accounting and
payout distribution. SV2 could support a more decentralized model, but
we have not yet seen a pool designed for it.

This is where the rubber meets the road. A pool that decides the block
reward distribution holds a lever over its miners' transaction
selection. Under pressure from a regulator, a centralized pool
operator can be compelled to refuse payment to any miner that includes
transactions involving the addresses or Script constructions the
regulator wants suppressed.

The diagram below shows a centralized pool operator, under pressure
from a regulator, refusing to pay a miner for its work. The miner must
then drop the transaction or leave the pool.

[plantuml, datum-sv2-payout-refused, svg]
.The pool leaves a miner out of the payout
....
@startuml
actor Regulator as R
participant "Pool operator\n(DATUM / SV2 JD server)" as P
participant "Miner A\n(own bitcoind)" as A
participant "Miner B\n(own bitcoind)" as B

R -[#E5484D]> P : suppress transactions\ninvolving address X
A -> A : build template with\ntransaction paying X
B -> B : build template\nwithout X
A -> P : submit shares
B -> P : submit shares
P -[#E5484D]> P : compute payouts,\nleave out Miner A
alt DATUM
  P -[#E5484D]> A : next coinbase outputs\n(Miner A left out)
  P -> B : next coinbase outputs\n(Miner B included)
else SV2 Job Declaration
  P -[#E5484D]> P : withhold Miner A's\naccount balance
  P -> B : pay Miner B\nfrom pool wallet
  note over P : coinbase-only mode: the pool\nonly sees X once Miner A\nfinds a block
end
A -[#E5484D]> A : leave pool
@enduml
....

== Pools Can Reject Jobs

The DATUM server validates the shares it accepts, so it has the final
say over which block templates count as valid work.

In the full-template mode of SV2 Job Declaration, the pool operator
can reject jobs outright, as OCEAN can with DATUM.

The coinbase-only mode of SV2 Job Declaration, however, lets a miner
mine without sending its transaction list to the pool operator, so the
pool cannot reject the work outright. It is the most
censorship-resilient mode available to SV2 pools, and P2Poolv2 makes
it the baseline guarantee for permissionless mining.

[plantuml, datum-sv2-work-rejected, svg]
.Whether the pool can reject work depends on what it can see
....
@startuml
actor Regulator as R
participant "Pool operator\n(DATUM / SV2 JD server)" as P
participant "Miner A\n(own bitcoind)" as A

R -[#E5484D]> P : suppress transactions\ninvolving address X
A -> A : build template with\ntransaction paying X
alt DATUM / SV2 full-template
  A -> P : declare job / submit share\n(transactions visible)
  P -[#E5484D]> P : check template\nagainst blocklist
  P -[#E5484D]-> A : rejected: template includes\nsuppressed transaction
  note over A : Miner A's work earns nothing\nunless it drops the transaction
else SV2 coinbase-only
  A -> P : declare coinbase / submit share\n(no transaction list)
  P --> A : accepted: pool can't\nsee transaction X
  note over P : Pool has to respond to the regulator
end
@enduml
....

== P2Poolv2 Decentralized Accounting

P2Poolv2 instead runs accounting on a decentralized sharechain, a
blockchain of weak bitcoin blocks. Nakamoto consensus brings all miners
to the same view of the shares, so each miner can generate coinbase
payout distributions that every other miner can continuously and
independently validate.

== P2Poolv2 Non-Custodial Payouts

Miners are paid directly from coinbases or through an atomic swap
mechanism, so they never hand custody of their shares or rewards to a
pool operator. See xref:payouts/marketplace.adoc[Marketplace] for how
P2Poolv2 enables this.

P2Poolv2 can reject transactions only if miners who want them rejected
mount a 51% attack. The censored miners can then fork the pool and run
a separate P2Poolv2 chain.
